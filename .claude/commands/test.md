Задача:
Проверить решение и зафиксировать результаты — включая то, что не работает.

Создай отчёт в `docs/07-testing/reports/` с датой в имени файла.

## Обязательные проверки

**1. Девять презентаций.** По критериям приёмки из `deliverables.md`: открываются без ошибок, 10–15 слайдов, собраны на макетах своего шаблона, три варианта визуально различимы, ни один слайд не растровый, по каждой есть отчёт аудита.

**2. Нативность экспорта.** Открыть `.pptx` и убедиться, что текст, таблицы и диаграммы — редактируемые объекты. Слайд, оказавшийся изображением, — провал по прямому требованию ТЗ. Проверять выборочно по каждому шаблону, а не один файл на всю девятку.

**3. End-to-end на приёмочном шаблоне** из `assets/templates/acceptance/`. Это единственная фаза, где его использование уместно. Прогон делается на чистом состоянии, без предварительной подгонки под этот шаблон.

**4. Пограничный случай** из `assets/templates/edge-cases/`. Ожидаемое поведение описано в README этой папки: система должна сообщить, что дизайн-система не извлекается, а не молча собрать колоду в дефолтном офисном стиле.

**5. Лимит времени.** Генерация одной колоды — не более 5 минут. Замерять, а не оценивать. Отдельно замерить вклад недетерминированного аудита: он самый вероятный виновник превышения.

**6. Детерминированность.** Повторный запуск на том же входе с той же версией промптов должен дать тот же результат в детерминированной части: та же схема шаблона, те же координаты, те же находки детерминированного аудита. Это ключевое заявляемое свойство решения — если оно не выполняется, это самый важный дефект из возможных.

**7. Аудит находит реальные дефекты.** Взять слайд с заведомым дефектом (текст за границей, наложение блоков, цвет вне палитры) и убедиться, что проверка срабатывает. Аудит, который ничего не находит, не проверен — он просто молчит.

**8. Наследование свойств.** Шаблон без явных размеров шрифта на уровне прогонов должен обрабатываться корректно. На этом падает presenton (issue #794), и шаблон комиссии почти наверняка устроен так же.

## Требования к отчёту

- **Показывать вывод команд,** а не пересказ. Утверждение «тесты проходят» без вывода не считается результатом.
- **Фиксировать провалы явно.** Отчёт без единого дефекта на этом этапе означает, что проверка была недостаточной, а не что решение идеально.
- Для каждого дефекта: что делали, что ожидали, что получили, на каком шаблоне и варианте.
- Разделять дефекты по критичности: нарушение требования ТЗ — блокер; ухудшение качества — обычный дефект.
- Не исправлять найденное в рамках этой команды: дефекты заносятся в `tasks.md`.

Ограничения:
- Не менять продуктовый код.
- Не ослаблять проверки, чтобы они прошли. Если проверка не выполнима — сказать почему, а не переформулировать её мягче.
