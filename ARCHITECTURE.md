# Архитектура пайплайна

## Обзор

Пайплайн состоит из пяти логических слоёв, каждый из которых имеет чёткие входные и выходные контракты. Слои слабо связаны и могут заменяться независимо.

```text
┌─────────────────────────────────────────────────────────────┐
│                         Вход                                │
│  Бриф пользователя + Шаблон + Контент-пакет                 │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐
│  СЛОЙ 1: ПАРСИНГ                                            │
│  - Извлечение дизайн-системы из шаблона                     │
│  - Токены: цвета, шрифты, отступы, направляющие             │
│  - Композиционные паттерны и типы слайдов                   │
│  - Макеты и плейсхолдеры                                    │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐
│  СЛОЙ 2: ГЕНЕРАЦИЯ                                          │
│  - Понимание брифа                                          │
│  - Генерация структуры презентации (outline)                │
│  - Генерация текста для каждого слайда                      │
│  - Выбор типов слайдов                                      │
│  - Генерация запросов для визуализаций                      │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐
│  СЛОЙ 3: ВЕРСТКА                                            │
│  - Выбор макета под контент                                 │
│  - Применение дизайн-системы                                │
│  - Размещение текста, изображений, графиков, SmartArt       │
│  - Обработка переполнения                                   │
│  - Генерация 3 вариантов верстки                            │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐

│  - Детерминированные проверки (вёрстка, шаблон, плотность)  │
```

## Границы слоёв

ТЗ требует явного описания границ. Граница слоя — это контракт: формат данных на входе, формат на выходе и то, что слой принципиально **не** делает.

| Слой | Вход | Выход | Слой не делает |
|---|---|---|---|
| 1. Парсинг | Бинарный PPTX/POTX | `TemplateSchema` (JSON) | Не знает о контенте и брифе |
| 2. Генерация | Бриф + контент-пакет + `TemplateSchema` | `PresentationStructure` (JSON) | Не задаёт координаты и не выбирает цвета |
| 3. Верстка | `PresentationStructure` + `TemplateSchema` + параметры варианта | `RenderedPresentation` | Не вызывает LLM для финальной разметки |
| 4. Аудит | `RenderedPresentation` + `TemplateSchema` | `AuditReport` | Не правит слайды сам — только сообщает и предлагает |
| 5. Экспорт | `RenderedPresentation` | `.pptx` / `.html` / `.pdf` | Не меняет содержание и композицию |

### Ключевой принцип разделения

LLM отвечает за **смысл**: структуру повествования, тексты, выбор типа визуализации. Детерминированный движок отвечает за **форму**: координаты, цвета, шрифты, размеры, соответствие правилам шаблона. Граница между ними проходит по контракту `PresentationStructure` — в нём нет ни одной координаты и ни одного цвета.

Это даёт воспроизводимость: при фиксированном `PresentationStructure` слой верстки всегда даёт одинаковый результат, что делает возможными детерминированные проверки аудита.

## Инварианты, вытекающие из разбора калибровочных шаблонов

Разбор трёх шаблонов (см. `docs/01-research/template-analysis.md`) показал три свойства реальных корпоративных шаблонов, которые заданы как архитектурные инварианты.

**Инвариант 1. Координаты в `TemplateSchema` хранятся нормализованными.**
Холст калибровочных шаблонов различается: 9144000 EMU против 12192000 EMU по ширине при одном соотношении 16:9. Абсолютные координаты между шаблонами непереносимы, поэтому схема хранит доли от ширины и высоты холста, а EMU вычисляются на этапе экспорта.

**Инвариант 2. Дизайн-токены извлекаются из фактической разметки, а не только из темы.**
Во всех трёх шаблонах `theme1.xml` расходится с реальностью: тема объявляет `Arial`, фактически используется `Play`; в одном из шаблонов тема содержит дефолтную палитру Office вместо брендовой. Тема — лишь один из сигналов; решающим является частотный анализ фактических свойств с учётом уровня (мастер → макет → слайд).

**Инвариант 3. Слот не равен плейсхолдеру.**
В двух шаблонах из трёх у большинства макетов есть только плейсхолдер заголовка, а весь остальной контент размечен обычными фигурами. Слой верстки обязан уметь распознавать не-плейсхолдерные фигуры макета как слоты контента, иначе на таком шаблоне колода выродится в набор заголовков.

## Версионирование

Промпты и конфиги скиллов и агентов лежат отдельными файлами в `prompts/` и версионируются независимо от кода. Каждому запуску пайплайна соответствует зафиксированный набор версий, что обеспечивает воспроизводимость результата.
