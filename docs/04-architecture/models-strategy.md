# Стратегия применения моделей

Где применяется LLM, где VLM, где не применяется ничего, и как при этом соблюдается пятиминутный бюджет. Состав моделей, лицензии и системные требования — в корневом `MODELS.md`; этот документ описывает их применение и не дублирует их перечень.

Дата: 2026-09-29.

## Правило распределения

Модель применяется там, где нужен **смысл**. Там, где нужна **форма**, модель не применяется никогда.

| Этап | Модель | Почему так |
|---|---|---|
| Парсинг шаблона | **нет** | Разбор OOXML и частотный анализ — детерминированные операции |
| Верификация токенов | VLM, опционально | Узкий вопрос по рендеру: подтвердить уже извлечённое |
| Генерация структуры колоды | LLM | Смысл: что рассказывать и в каком порядке |
| Генерация содержания | LLM | Смысл: заголовки-выводы, тексты, план визуализаций |
| Аудит текста (4a) | LLM | Смысл: содержит ли заголовок вывод, прослеживаются ли цифры |
| Вёрстка | **нет** | Форма: координаты, макеты, компенсации |
| Генерация визуализаций | **нет** | Форма: оформление из токенов шаблона |
| Рендер слайдов | **нет** | Техническая операция |
| Аудит формы (4b) | **нет** | Проверки по данным файла |
| Аудит визуала (4c) | VLM | То, что видно только на изображении |
| Экспорт | **нет** | Детерминированная сборка файла |

Из одиннадцати этапов модели участвуют в пяти. Запрет на модели в вёрстке — не стилистика: если выбор макета станет вероятностным, детерминированный аудит потеряет смысл, потому что при повторном прогоне нарушения будут другими.

## Бюджет пяти минут

Решение D4: бюджет считается по полному циклу на незнакомом шаблоне, включая разбор. Ниже — расчёт для колоды из 12 слайдов и трёх вариантов вёрстки.

### Наивный вариант, который не проходит

Буквальное чтение Приложения 1 ТЗ — «на вход картинка слайда», все 11 вопросов валидации контента, все слайды, все варианты:

`11 вопросов × 12 слайдов × 3 варианта = 396 запросов к VLM`

При оптимистичных 2 секундах на запрос — 13 минут только на аудит. Бюджет превышен в два с половиной раза, и это без генерации.

### Принятый вариант

| Этап | Запросов | Параллелизм | Оценка, с |
|---|---|---|---|
| Парсинг шаблона | 0 | — | 10–30 |
| Верификация токенов (VLM) | 1–2 | — | 5–10 |
| Генерация структуры (LLM) | 1 | — | 15–30 |
| Генерация содержания (LLM) | 12, по слайду | 4 потока | 25–40 |
| Аудит текста (LLM) | 1 на колоду | — | 30–40 |
| Вёрстка × 3 | 0 | 3 потока | 3–10 |
| Рендер слайдов | 0 | см. примечание | **20–35** |
| Аудит формы × 3 | 0 | — | 1–3 |
| Аудит визуала (VLM) | 12, выбранный вариант | 4 потока | 15–30 |
| Экспорт в три формата | 0 | — | 5–15 |
| **Итого** | **27–29 запросов** | | **129–243** |

**Примечание о рендере.** Оценка скорректирована 2026-09-29 по измерению на реальном шаблоне: LibreOffice конвертирует колоду из 29 слайдов в PDF за 28 секунд, после чего `pymupdf` рендерит страницы по 0,11 с. Узкое место — конвертация, и она плохо параллелится: это один внешний процесс на колоду, а не задача на слайд. Первоначальная оценка в 7–15 секунд была занижена.

Меры на случай, если на нашей колоде подтвердится верхняя граница: держать LibreOffice запущенным как сервис и переиспользовать процесс; рендерить только выбранный вариант, что уже заложено. Подробности — `project-architecture.md`.

Около двух-четырёх минут при бюджете пять. Запас нужен: оценки получены из типичных времён инференса, а не из измерений на целевом железе — измерения будут на фазе тестирования.

### Четыре приёма, которые дали этот результат

**1. Аудит текста выполняется один раз, а не трижды.** Три варианта строятся на одном контенте (требование ТЗ), поэтому смысловые проверки текста дадут для них идентичный результат. Заголовок либо содержит вывод, либо нет — независимо от макета.

**2. Аудит текста выполняется до вёрстки, а не после.** Находки этого класса правятся перегенерацией текста. Обнаружив их после вёрстки трёх вариантов, мы выбросили бы работу трёх вариантов.

**3. Все вопросы по слайду задаются одним запросом.** Не 11 запросов на слайд, а один с 11 вопросами и структурированным ответом. Экономия — порядок величины.

**4. Аудит визуала — только для выбранного варианта.** Проверки формы, которые действительно различаются между вариантами, выполняются детерминированно и бесплатно для всех трёх. VLM нужен лишь там, где код цвета не существует или где оценивается уместность картинки — и это применяется к варианту, который пользователь собирается экспортировать. Полный прогон по всем трём доступен по явному требованию.

### Деградация при превышении (EF-9)

Порядок урезания, если бюджет исчерпывается:

1. Аудит визуала переводится на выборку слайдов вместо всех.
2. Верификация токенов пропускается.
3. Аудит текста переводится на батч из нескольких слайдов в одном запросе.

Детерминированные проверки не урезаются никогда: они дешёвые и составляют доказуемую часть аудита. Любое урезание фиксируется в `AuditReport` явно — отчёт, умолчавший о сокращении проверок, хуже отсутствующего.

## Требования к вызову моделей

**Строгий JSON на выходе.** Каждый вызов сопровождается JSON-схемой ожидаемого ответа. Невалидный ответ не передаётся дальше: выполняется повторный запрос с указанием ошибки, число попыток ограничено. После исчерпания попыток — внятная ошибка с указанием этапа (EF-8), а не частичный результат.

**Абстракция от модели.** Клиент принимает системный промпт, запрос и схему ответа; какая модель за этим стоит — его деталь. Это нужно для того, чтобы переход с модели отборочного этапа на модель организаторов не потребовал правок в промптах и коде.

**Минимальная температура и фиксированный seed** там, где провайдер это поддерживает. Полной воспроизводимости это не даёт — недетерминированная часть остаётся недетерминированной, — но уменьшает разброс между прогонами. Заявлять воспроизводимость мы будем только для детерминированной части (NFR-6).

**Промпты вне кода.** Все системные промпты и схемы ответов лежат файлами в `prompts/skills/`, версия набора фиксируется в `AuditReport`. Без этого утверждение о воспроизводимости непроверяемо: неизвестно, какими промптами получен результат.

## Разделение ролей между LLM и VLM

| | LLM | VLM |
|---|---|---|
| Что подаётся | текст: бриф, контент-пакет, `PresentationStructure` | изображение слайда плюс короткий вопрос |
| Что спрашивается | смысл, структура, формулировки | то, что видно только глазами |
| Объём ответа | большой: структура колоды, тексты | маленький: набор «да/нет» с пояснениями |
| Стоимость | высокая по токенам вывода | высокая по латентности на изображение |

Из разницы в профиле стоимости следует практический вывод: LLM экономят, укрупняя запросы (вся колода за раз), а VLM — сокращая число изображений. Приёмы 3 и 4 выше построены именно на этом.

## Отвергнутые варианты

**Одна модель на всё, включая аудит по изображениям.** Отвергнуто: VLM на 7B хуже LLM на 32B в работе со структурой и связным текстом, а гонять 32B-модель на каждое изображение слишком дорого по латентности. Разделение ролей дешевле и точнее.

**LLM для выбора макета** («покажи модели список макетов, пусть выберет подходящий»). Отвергнуто: ломает воспроизводимость вёрстки и вместе с ней детерминированный аудит. Допустимая уступка — ранжирование макетов-кандидатов моделью с окончательным детерминированным выбором; в текущем объёме не используется.

**VLM-реконструкция шаблона вместо парсинга** — подход presenton. Отвергнуто в `solution-architecture.md`, решение 4: результат невоспроизводим и отказывает на шаблонах с наследуемой типографикой. Сильная сторона их подхода компенсирована опциональной верификацией токенов.

**Аудит каждого варианта через VLM.** Отвергнуто по арифметике выше: 396 запросов против бюджета в 5 минут.

## Открытые вопросы, влияющие на стратегию

- **Q1–Q3:** модель организаторов не идентифицирована, форма предоставления неизвестна. Стратегия построена так, чтобы смена модели была заменой конфигурации, а не переделкой.
- **T8 решён на фазе 6:** введён третий класс проверок `rendered` — по изображению, но алгоритмом, а не моделью. Контраст выполняется как `file` при сплошном фоне и как `rendered` при фоне-изображении. См. `audit-architecture.md`.
