# ADR-0002. Синхронный пайплайн и распределение бюджета времени

**Статус:** принято
**Дата:** 2026-09-29
**Фаза:** 5 (архитектура решения)

## Контекст

ТЗ ограничивает время генерации колоды пятью минутами. Решением D4 бюджет считается по полному циклу на незнакомом шаблоне: разбор, генерация, вёрстка, аудит, экспорт.

Буквальное чтение Приложения 1 ТЗ требует выполнять контекстуальные проверки по изображению каждого слайда. Для колоды из 12 слайдов, трёх вариантов и 11 вопросов валидации это 396 запросов к VLM — около 13 минут при оптимистичной оценке, то есть бюджет превышен в два с половиной раза только на аудите.

Многопользовательность прямо вынесена за границы проекта уставом. Решение D7 требует выбирать более простой вариант при равных.

## Решение

**Пайплайн синхронный:** один линейный проход в рамках одного запроса, с потоковой отдачей событий прогресса по этапам и записью времени каждого этапа в `AuditReport` (требование NFR-1а).

**Внутренний параллелизм разрешён:** три варианта вёрстки, генерация содержания по слайдам, рендер слайдов и запросы к VLM выполняются параллельно. Это параллелизм внутри этапа, а не асинхронность архитектуры.

**Бюджет соблюдается четырьмя приёмами** (расчёт — в `models-strategy.md`):

1. аудит текста выполняется один раз на колоду, а не для каждого из трёх вариантов, поскольку все три построены на одном контенте;
2. аудит текста выполняется до вёрстки — иначе работа трёх вариантов выбрасывается при первой смысловой находке;
3. все вопросы по слайду задаются одним запросом со структурированным ответом, а не одним запросом на вопрос;
4. аудит визуала выполняется для выбранного варианта; полный прогон по трём — по явному требованию пользователя.

Итог расчёта: 27–29 запросов к моделям и 116–223 секунды против бюджета 300.

**Обратная связь ограничена одной операцией** «перегенерировать слайд N», проходящей подпайплайн только для этого слайда.

**Порядок деградации при исчерпании бюджета** (EF-9): выборка слайдов в аудите визуала → отказ от верификации токенов → батчинг аудита текста. Детерминированные проверки не урезаются никогда. Любое урезание фиксируется в отчёте.

## Отвергнутые варианты

**Асинхронная обработка через брокер и воркеры.** Отвергнуто: понадобилась бы для одновременного приёма многих заданий, а многопользовательность вне границ проекта. Пользователь всё равно ждёт результат — ему нечего делать, пока колода не собрана. Добавляет брокер, воркеры и внешнее состояние при решении D7 о упрощении.

**Аудит по изображениям для всех вариантов и всех вопросов,** как читается Приложение 1 буквально. Отвергнуто по арифметике: физически не укладывается в бюджет.

**Отказ от лимита времени как от второстепенного.** Отвергнуто: это прямое требование «Рамок решения» ТЗ и один из пунктов критерия оценки № 4 («устойчивость, скорость»).

**Мягкая трактовка бюджета** — считать только генерацию по уже разобранному шаблону. Отвергнуто решением D4: на защите прогон пойдёт на незнакомом шаблоне с нуля, и секундомер покажет полное время независимо от трактовки.

## Последствия

**Положительные.** Архитектура проще: нет брокера, воркеров и внешнего состояния. Разбивка времени по этапам служит доказательством соблюдения лимита на защите и одновременно показывает узкое место. Все проверки Приложения 1 сохранены — изменилось только то, на каком представлении и сколько раз они выполняются.

**Отрицательные.** Один прогон занимает процесс целиком: параллельная генерация нескольких колод потребует запуска нескольких процессов. Для девяти демонстрационных колод это означает батч-режим с последовательным или процессным параллелизмом, а не очередь задач.

**Риск.** Оценки времени получены из типичных значений латентности инференса, а не из измерений на целевом железе. Если реальные времена окажутся вдвое выше, запас исчезнет. Измерение — обязательный пункт фазы тестирования, а порядок деградации задан заранее именно на этот случай.

**Точка расширения сохранена.** Этапы пайплайна — независимые преобразования с сериализуемыми контрактами; развести их по воркерам можно без изменения контрактов.
