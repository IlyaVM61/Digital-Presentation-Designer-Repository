# Архитектура решения

Общая картина: компоненты, поток данных, состояние, оркестрация, точки расширения. Границы слоёв и инварианты заданы в корневом `ARCHITECTURE.md` и здесь не пересматриваются. Детализация слоёв — `pipeline-architecture.md`.

Дата: 2026-09-29. Требования — `docs/03-product/prd.md`.

## Ключевая идея

Система состоит из двух принципиально разных частей, и вся архитектура построена вокруг границы между ними.

**LLM отвечает за смысл:** что рассказывать, в каком порядке, какими словами, какой тип визуализации уместен. **Детерминированный движок отвечает за форму:** какой макет, какие координаты, какие цвета и кегли, помещается ли содержимое.

Граница проходит по контракту `PresentationStructure`, в котором нет ни одной координаты и ни одного цвета. Это не стилистическое предпочтение: на воспроизводимости формы держится детерминированный аудит, а он — требование ТЗ. Если движок начнёт спрашивать модель, куда поставить блок, проверка «блок не выровнен по направляющим» потеряет смысл, потому что при повторном прогоне результат будет другим.

## Решение 1: аудит разделён на три подслоя, а не на два

Приложение 1 ТЗ делит проверки на детерминированные и недетерминированные. Этого деления недостаточно для архитектуры, потому что недетерминированные проверки бывают двух совершенно разных видов.

| Подслой | Что проверяет | Чем | Когда | Сколько раз |
|---|---|---|---|---|
| 4a. Аудит текста | Смысл: заголовок содержит вывод, цифры из источника, язык один, слайды связаны логически | LLM по `PresentationStructure` | **до вёрстки** | один раз на колоду |
| 4b. Аудит формы | Вёрстка, шаблон, плотность, целостность | детерминированно по `RenderedPresentation` | после вёрстки | для каждого из трёх вариантов |
| 4c. Аудит визуала | То, что видно только на картинке: уместность изображений, читаемость, контраст на фоне-изображении | VLM по рендеру слайда | после вёрстки | только для выбранного варианта |

**Обоснование.** Три варианта вёрстки строятся на **одном и том же контенте** — это прямое требование ТЗ. Значит смысловые проверки текста дадут для них идентичный результат: заголовок либо содержит вывод, либо нет, независимо от того, в каком макете он лежит. Выполнять их трижды — тройная трата самого дорогого ресурса.

Более того, выполнять их **после** вёрстки поздно: если заголовок не несёт вывода, это правится перегенерацией текста, а вёрстка всех трёх вариантов к этому моменту уже потрачена впустую.

**Отвергнутая альтернатива:** единый недетерминированный аудит по изображениям слайдов, как предполагает буквальное чтение Приложения 1 («на вход — картинка слайда»). Отвергнут по арифметике: 11 вопросов × 15 слайдов × 3 варианта = 495 запросов к VLM. При оптимистичных 2 секундах на запрос это 16 минут против бюджета в 5 минут на весь цикл. Такой аудит физически неосуществим.

Разделение сохраняет требование ТЗ полностью: все проверки Приложения 1 выполняются, меняется только то, на каком представлении и сколько раз.

## Решение 2: синхронный пайплайн с потоковым прогрессом

Пайплайн выполняется как один линейный проход в рамках одного запроса, с отдачей событий прогресса по этапам.

**Обоснование.** Бюджет — 5 минут на полный цикл (решение D4), и пользователь всё это время ждёт результат: ему нечего делать в интерфейсе, пока колода не собрана. Очередь задач с воркерами понадобилась бы, чтобы принимать много заданий одновременно, а многопользовательность прямо вынесена за границы проекта в уставе.

События прогресса нужны не для красоты: NFR-1а требует разбивки времени по этапам, а она же служит доказательством соблюдения лимита на защите.

**Отвергнутая альтернатива:** асинхронная обработка через брокер и воркеры. Отвергнута как переусложнение при решении D7 (курс на упрощение) и при отсутствии требования многопользовательности. Точка расширения сохраняется: этапы пайплайна — независимые преобразования, их можно развести по воркерам, не меняя контракты.

**Внутренний параллелизм разрешён и нужен:** три варианта вёрстки не зависят друг от друга, как и рендер отдельных слайдов для VLM. Это параллелизм внутри этапа, а не асинхронность архитектуры.

## Решение 3: состояние — файловое, без базы данных

| Артефакт | Где живёт | Время жизни |
|---|---|---|
| `TemplateSchema` | кеш на диске, ключ — хеш файла шаблона | до изменения шаблона |
| `PresentationStructure` | файл в рабочем каталоге прогона | прогон |
| `RenderedPresentation` × 3 | файлы в рабочем каталоге прогона | прогон |
| Рендеры слайдов (изображения) | файлы в рабочем каталоге прогона | прогон |
| `AuditReport` | файл рядом с результатом | постоянно, часть артефактов сдачи |
| Экспорт | `out/` | постоянно |

**Обоснование.** Каждый промежуточный артефакт — файл, который можно открыть и посмотреть. Это ровно то, что нужно на защите: ТЗ требует показать устройство проверок, и «вот схема шаблона, вот структура презентации, вот отчёт аудита» убедительнее словесного описания. Плюс упрощение (D7): нет миграций, нет схемы БД, нет отдельного сервиса.

**Кеширование схемы шаблона по хешу файла** решает практическую задачу: девять колод генерируются на трёх шаблонах, и разбирать каждый шаблон трижды незачем. При этом первый прогон на незнакомом шаблоне идёт полным циклом — именно так, как будет на защите.

**Отвергнутая альтернатива:** SQLite или Postgres для состояния. Отвергнута: у нас нет ни поиска по данным, ни конкурентного доступа, ни пользователей — единственное, что дала бы БД, это дополнительная зависимость.

## Решение 4: VLM применяется для верификации, а не для реконструкции

Это ответ на объективно сильную сторону presenton, которую нельзя игнорировать.

Presenton реконструирует шаблон vision-моделью по скриншотам слайдов. Такой подход **естественно обходит** проблему, которая нам стоила отдельного исследования: модель смотрит на отрендеренный слайд и видит фактическое оформление, а не заявленное в теме. Наш детерминированный парсер видит XML, где тема утверждает `Arial`, а фактически используется `Play` — и мы обязаны разрешить этот конфликт правилами.

Правила частотного анализа со взвешиванием по уровню решают задачу, но не дают гарантии. Поэтому в архитектуру вводится **опциональный шаг верификации**: после извлечения токенов один-два отрендеренных слайда-примера шаблона показываются VLM с узким вопросом вида «какая гарнитура использована в заголовке: Play или Arial».

Это принципиально иное применение модели, чем у presenton: она не строит дизайн-систему, а подтверждает или опровергает уже построенную детерминированно. Стоимость — один-два запроса на шаблон, причём результат кешируется вместе со схемой. Расхождение не переписывает схему автоматически, а понижает `confidence` токена и попадает в предупреждения для пользователя.

**Отвергнутая альтернатива:** доверять только XML. Отвергнута потому, что мы сами измерили расхождение темы и разметки во всех четырёх проверенных шаблонах — игнорировать известный источник ошибок было бы неосмотрительно.

**Вторая отвергнутая альтернатива:** реконструировать шаблон через VLM, как presenton. Отвергнута: результат невоспроизводим, а на воспроизводимости держится весь детерминированный аудит. Кроме того, их подход отказывает на шаблонах с наследуемой типографикой (issue #794) — то есть на всех трёх калибровочных.

## Решение 5: перегенерация — срез по одному слайду, а не полный цикл

Решение D5 сделало аудит нетерминальным: смысловые находки закрываются перегенерацией слайда. Это вводит в линейный пайплайн обратную связь, и её нужно ограничить.

Оркестратор поддерживает операцию «перегенерировать слайд N», которая проходит подпайплайн только для этого слайда: генерация содержания слайда → вёрстка слайда → аудит слайда. Остальные слайды не трогаются, структура колоды сохраняется.

**Обоснование.** Полный перезапуск пайплайна из-за одного слайда сжёг бы бюджет времени и изменил бы слайды, которые пользователя устраивали. Срез по слайду делает операцию предсказуемой: пользователь видит, что меняется ровно то, что он попросил.

**Ограничения цикла** (из D5): исправление, создающее находку не ниже по критичности, не применяется; число итераций ограничено; остаточные находки показываются как есть.

## Компоненты

| Компонент | Ответственность | Модели |
|---|---|---|
Оркестратор | Последовательность этапов, события прогресса, замер времени, операция перегенерации слайда | нет |
| Парсер шаблона | OOXML → `TemplateSchema` | нет |
| Верификатор токенов | Подтверждение извлечённых токенов по рендеру | VLM, опционально |
| Генератор структуры | Бриф + контент → состав и последовательность слайдов | LLM |
| Генератор содержания | Тексты слайдов, планы визуализаций | LLM |
| Аудитор текста | Смысловые проверки по структуре | LLM |
| Движок вёрстки | Выбор макета, размещение, переполнение, три варианта | нет |
| Генератор визуализаций | Диаграммы, таблицы, схемы, пиктограммы из токенов | нет |
| Рендерер | Слайд → изображение для VLM и превью | нет |
| Детерминированный аудитор | Проверки вёрстки, шаблона, плотности, целостности | нет |
| Аудитор визуала | Проверки, требующие изображения | VLM |
| Фиксер | Применение исправлений по политике D5 | нет |
| Экспортёры | `.pptx` нативными объектами, `.html`, `.pdf` | нет |

Из тринадцати компонентов модели используют четыре. Это прямое следствие ключевой идеи: смысл — моделям, форма — коду.

## Точки расширения

Заложены интерфейсом, но не реализуются в текущем объёме:

- **Генерация изображений внутри слайда** (FR-27, задача со звёздочкой, исключена решением D7). Генератор визуализаций получает тип «изображение» в плане визуализации; сейчас такой план не строится.
- **Дополнительные проверки аудита.** Проверка — самостоятельная единица с категорией, классом исправимости и уверенностью; добавление проверки не меняет остальные слои.
- **Новые форматы экспорта.** Экспортёр читает `RenderedPresentation`, ничего не зная о предыдущих слоях.
- **Альтернативные провайдеры моделей.** Клиент модели абстрагирован: на входе системный промпт, запрос и JSON-схема, на выходе валидный JSON.
- **Асинхронная оркестрация.** Этапы — независимые преобразования, их можно развести по воркерам без изменения контрактов.

## Проверка на неизвестном шаблоне

Каждое решение проверено вопросом «выдержит ли оно шаблон, которого мы не видели».

| Свойство неизвестного шаблона | Что его выдерживает |
|---|---|
| Другой холст, другое соотношение сторон | Нормализованные координаты, пересчёт только при экспорте |
| Тема не настроена или противоречит разметке | Токены из фактической разметки, `confidence`, опциональная VLM-верификация |
| У макетов только плейсхолдер заголовка | Слот как абстракция над фигурой, стратегия `geometry-first` |
| Имена макетов дублируются | Тип макета из геометрии, `nameIsReliable` |
| Нет явных размеров шрифта | Разрешение цепочки наследования |
| Нет макетов под нужный тип слайда | Деградация типа с фиксацией в отчёте (FR-19) |
| Фон — изображение | `background.contrastComputable`, гибридная проверка контраста |
| Дизайн-системы нет вовсе | Предупреждение пользователю вместо молчаливой сборки в дефолтном стиле (EF-6) |

## Что решается не здесь

- Стек, библиотеки, структура каталогов — фаза 9 (решение D6).
- Полный перечень проверок аудита и их классификация — фаза 6.
- Ось различий трёх вариантов вёрстки — фаза 7 (решение D2).
