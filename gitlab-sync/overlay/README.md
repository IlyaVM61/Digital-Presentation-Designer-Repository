# Цифровой дизайнер презентаций

ИИ-помощник, который собирает редактируемую презентацию `.pptx` по корпоративному шаблону из текстового описания: бриф — для кого и зачем презентация, материалы — тезисы, цифры, таблицы.

Система читает шаблон как набор правил — макеты, шрифты, кегли, фирменные цвета — и верстает по ним новые слайды. Модель пишет смысл: структуру колоды, текст слайдов, выбор между таблицей и диаграммой. Форму задаёт детерминированный движок: какой макет, где блок, каким шрифтом и цветом. На выходе три варианта колоды в `.pptx`, `.pdf` и `.html`; текст, таблицы и диаграммы в `.pptx` — родные объекты PowerPoint, ни одного слайда картинкой.

> **Принцип этой сдачи — всё, что мы показываем, сделал сам сервис.** Примеры и даже презентацию о решении собрала наша система на корпоративном шаблоне. Мы сознательно вложились в смысл и механику — разбор шаблона, сверку чисел с источником, аудит, редактируемый `.pptx`, — а не в оформление. Чего сервис пока не умеет, руками не дорисовываем: изображений на этой стадии нет, поэтому их нет ни в примерах, ни в презентации. Слайды выглядят скромно — это честный результат системы, а не ручная вёрстка. В презентации о решении руками поправлен только текст нескольких слайдов, и она сама об этом говорит.

## Сервис по ссылке

**Ссылка на сервис и демонстрационная учётная запись указаны в карточке решения на платформе** — в репозиторий они не входят. Браузер спросит логин и пароль при первом открытии.

Сервер размещён в России. Если страница не открывается при включённом VPN, откройте её без VPN.

Что делать на странице:

1. **Шаблон презентации** — загрузите корпоративный шаблон `.pptx` как есть, без подготовки. Страница покажет, что прочитала: число макетов, шрифт, фирменные цвета.
2. **Содержание** → «Написать по брифу и материалам» — загрузите бриф и материалы файлами `.md` или `.txt`. Распределять текст по слайдам не нужно. Заголовки Markdown делят материалы на разделы: слайд ссылается на раздел, и числа слайда сверяются с ним; таблицы — в разметке Markdown. Готовые входные данные — в папке `examples/` (раздел «Примеры»). Второй путь — «Взять мой план»: заголовки и пункты пишете сами, модель не нужна, сборка — секунды.
3. **В каких форматах скачать** — PowerPoint, PDF, HTML. «Превью слайдов» показывает три варианта рядом.
4. **Собрать презентацию.** Колода из 10–13 слайдов собирается **9–19 минут**; почти всё это время модель пишет и проверяет текст.
5. **Три варианта** стоят рядом, слайд к слайду. Выберите один — «Какой вариант берёте».
6. **Что стоит поправить** — замечания проверки. Механические исправлены автоматически; где исправление чем-то жертвует, способ выбираете вы — «Исправить выбранное».
7. **Проверить, как выглядят слайды** — по кнопке модель смотрит на изображения слайдов выбранного варианта: виден ли текст. Около полуминуты.
8. **Скачать** `.pptx`, `.pdf`, `.html`.

Модели уходит только текст брифа и материалов, а по кнопке проверки — изображения слайдов. Сам шаблон модели не отправляется.

## Примеры

Папка `examples/` — три примера: бриф и материалы, как их загружают на странице, и готовая колода — три варианта в `.pptx`, `.pdf`, `.html`. Все собраны этим сервисом на корпоративном шаблоне, без правок кода; время — то, что пишет страница, от нажатия «Собрать» до трёх вариантов.

| Пример | Что показывает | Слайдов | Время |
|---|---|---|---|
| `examples/01-navigator/` — защита пилотной программы наставничества | смешанный материал: текст, цифры, таблица «до и после», два числовых ряда | 12 | 773 с |
| `examples/02-qa/` — ответы экспертов трека на вопросы участников | обычный текст без таблиц | 13 | 572 с |
| `examples/03-tables/` — итоги года условного контактного центра | табличные данные: четыре таблицы | 10 | 755 с |

Каждое число в ячейках таблиц и в рядах диаграмм всех колод найдено в материалах примера. Что в примерах получилось плохо, перечислено в `examples/README.md` и в разделе «Ограничения».

## Запуск

Нужны Python 3.12 и LibreOffice — он делает `.pdf` и превью слайдов (https://www.libreoffice.org). Без LibreOffice собираются `.pptx` и `.html`.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r scripts/requirements.txt   # Windows: .venv\Scripts\python
.venv/bin/python -m pip install -e .                          # обязательно: пакет живёт в src/

cp .env.example .env            # вписать LLM_API_KEY — ключ провайдера модели
export DPD_OUTPUT_DIR=./out     # куда писать колоды, превью и кеш разбора шаблонов

.venv/bin/streamlit run ui/app.py
```

Страница откроется в браузере, порт по умолчанию — 8501. Без `pip install -e .` код не найдёт пакет `dpd` и упадёт с `ModuleNotFoundError` — это сетап, а не ошибка в коде.

| Переменная | Зачем |
|---|---|
| `LLM_API_KEY` | ключ провайдера модели; из `.env` или окружения |
| `LLM_BASE_URL`, `LLM_MODEL`, `VLM_BASE_URL`, `VLM_MODEL`, `VLM_API_KEY` | замена модели — раздел «Замена модели» |
| `DPD_OUTPUT_DIR` | каталог результатов; задаётся в окружении процесса |
| `SOFFICE_PATH` | путь к LibreOffice, если его нет в `PATH` |
| `HTTPS_PROXY` | прокси до провайдера модели, если он недоступен из вашей сети |

Файл `.env` читается только для настроек модели; остальные переменные задаются в окружении процесса.

Проверить доступ к модели — `python scripts/check_provider.py`. Тесты — `pytest`; модель они не вызывают, часть пропускается: им нужны шаблоны, которых в репозитории нет.

Развернуть сервис на своём сервере с HTTPS и паролем — `deploy/README.md`: Ubuntu 24.04, установка одной командой, выкладка — `deploy/deploy.sh`.

## Подготовка шаблона

**Размечать ничего не нужно.** Загрузите шаблон как есть: система сама читает мастер, макеты и их поля, а оформление берёт из того, что фактически стоит на слайдах шаблона. Тема файла часто расходится с оформлением — например, объявляет Arial, а на слайдах другой шрифт; тогда система берёт шрифт со слайдов и называет свой выбор на странице. Переключить на объявленное темой — `conflict_rule: template` в `configs/layout.yaml`.

Что берётся из шаблона:

- макеты и мастер — фон, декор, поля заголовка, текста, таблицы, картинки, номер слайда;
- шрифт, шкала кеглей, фирменные цвета, маркер списка — частотным разбором разметки;
- места под содержимое — из полей макета, а где полей нет — строятся в свободной области макета в обход декора.

Готовые слайды внутри шаблона — образцы оформления, диаграмм, иконок — пока не используются: колода собирается из макетов. Их можно оставить или удалить.

**Что можно менять в шаблоне** — всё: макеты, их число и порядок, цвета, шрифты, декор, поля. Разбор привязан к содержимому файла, поэтому изменённый шаблон читается заново при загрузке.

Что помогает системе:

- **Места под текст и таблицы — полями (плейсхолдерами) макета**, а не обычными надписями: поле — явное указание автора, где содержимое.
- **Номер слайда и дата — полями**: плейсхолдером номера или надписью с полем номера или даты. Такие места система под текст не занимает.
- **Шрифты шаблона установлены** на машине, где работает сервис. Иначе `.pdf` и превью получат замену шрифта; в `.pptx` шрифт шаблона сохраняется.

**По желанию — договорённость об именах макетов.** Если имена всех макетов шаблона начинаются с префикса назначения, назначение берётся из имени, а не угадывается по расположению полей:

| Префикс имени макета | Назначение |
|---|---|
| `title` | обложка |
| `section` | раздел |
| `slide` | обычный слайд |
| `table` | слайд с таблицей |
| `last` | финал |

Префикс пишется строчными: `title_main`, `slide_two_columns`. Договорённость действует, только когда ей следуют **все** макеты, — иначе имена не учитываются: редакторы дают многим макетам одно и то же имя по умолчанию. Поля по договорённости должны быть плейсхолдерами — заголовок, текст, таблица, картинка. Пока изображения не генерируются, макет с полем картинки уступает макету того же назначения без него. Переименовать макет в PowerPoint — «Вид → Образец слайдов», правой кнопкой по макету — «Переименовать макет».

На странице под «Подробности для дизайнера» видно, как прочитан шаблон: макеты и места в них, ведущий шрифт и уверенность в нём, палитра, шкала кеглей, качество разметки.

## Замена модели

Две роли: `llm` пишет структуру колоды и текст слайдов, `vlm` смотрит на изображения слайдов. По умолчанию — `qwen/qwen3-32b` и `qwen/qwen3-vl-32b-instruct` через OpenRouter: открытые веса, лицензия Apache 2.0. Почему они — `MODELS.md`.

**Модель меняется без правки кода** — переменными в `.env` или в окружении процесса:

```text
LLM_BASE_URL=адрес API провайдера          # по умолчанию https://openrouter.ai/api/v1
LLM_MODEL=имя модели у провайдера
LLM_API_KEY=ключ
VLM_BASE_URL=адрес API для модели, которая смотрит на слайды
VLM_MODEL=имя модели
VLM_API_KEY=ключ                           # без него берётся LLM_API_KEY
```

Что нужно от модели и провайдера:

- API, совместимый с OpenAI Chat Completions (`/chat/completions`);
- ответ в JSON: клиент передаёт схему ответа в `response_format`, сам проверяет ответ по контракту и просит модель исправить невалидный — до трёх попыток;
- для `vlm` — приём изображений.

Остальные параметры запросов — температура, seed, лимит токенов, число попыток, тайм-аут — в `configs/models.yaml`. Там же `extra` — параметры, которые понимает только OpenRouter: рассуждение модели включено, запрос идёт только тем провайдерам, что выполняют все его параметры. У другого провайдера `extra` очищается или заменяется его параметрами — это правка конфига, а не кода; пример для локального vLLM с Qwen3 — в комментарии файла. Промпты лежат отдельно, в `prompts/`, с версиями, и от модели не зависят. После замены стоит собрать одну колоду живым прогоном.

Время сборки почти целиком — время модели: более быстрая модель или провайдер ускоряют сборку без других изменений.

## Как это устроено

- **Разбор шаблона** разрешает наследование свойств — прогон, абзац, макет, мастер, тема — и извлекает оформление частотным анализом разметки, а не из темы файла.
- **Модель пишет смысл, движок — форму.** Между ними контракт без координат и цветов: роль, заголовок, ключевая мысль и содержимое каждого слайда. Поэтому вёрстка воспроизводима, и её можно проверять детерминированно.
- **Сверка чисел.** Каждое число на слайде сверяется с разделом материалов, на который слайд ссылается. Число, которого в материалах нет, со слайда убирается, а проверка текста его называет.
- **Таблицы и диаграммы** — родные объекты PowerPoint с данными из материалов; заливки, цвета подписей и контраст задаются по палитре шаблона.
- **Три варианта** различаются визуальным регистром: макет, цветовая схема макета, подача данных, кегль.
- **Аудит внутри пайплайна** — 37 проверок. Детерминированные: вёрстка, соответствие шаблону, плотность, целостность, контраст. Контекстуальные — моделью: текст колоды до вёрстки и изображения слайдов выбранного варианта. Механические находки исправляются автоматически, с откатом, если исправление ухудшило слайд; находки с потерями решает пользователь.

Подробнее — `ARCHITECTURE.md` (пайплайн и границы слоёв), `AUDIT.md` (проверки), `MODELS.md` (модели). Ссылки внутри этих файлов на каталог docs ведут в рабочую документацию проекта, которой в этом репозитории нет.

## Ограничения

- **Изображений нет:** картинки не генерируются и не подбираются. Макет с полем картинки уступает макету того же назначения без него.
- **Совместимость `.pptx` с офисным пакетом заказчика проверена в OnlyOffice Desktop 9.4** — на том же движке. Колода из 12 слайдов с текстом, списками, двумя таблицами и двумя диаграммами открывается, выглядит как в LibreOffice, правка текста и ячейки таблицы с сохранением прошла без потерь. Сам офисный пакет заказчика не проверялся; правка данных диаграммы в редакторе — тоже.
- **Время сборки — 9–19 минут** на колоду из 10–13 слайдов на нашем сервисе (572–1110 с). Текст слайдов модель пишет 6–12 минут, проверяет — 2–7; разбор шаблона, вёрстка и экспорт — секунды, превью — до полуминуты. Сервер один, 2 ядра и 4 ГБ памяти: две сборки одновременно идут медленнее.
- **Модель на нашем сервере идёт через прокси за рубежом:** OpenRouter не обслуживает адреса в России. Если прокси недоступен, текст по брифу не пишется; сборка по своему плану, три варианта, аудит и выгрузка работают без модели.
- **Объём колоды из брифа не читается:** колода всегда 10–15 слайдов, даже если бриф просит меньше.
- **Сверка чисел проверяет, что число есть в материалах, но не то, к чему оно относится.** В примере с таблицами модель написала «снижение на 3,4%», взяв 3,4 из соседней строки — роста затрат прошлого года; проверка текста это не заметила.
- **Варианты различаются меньше, когда в шаблоне один макет для обычного слайда:** тогда в основном кеглем, а не макетом — так на корпоративном шаблоне.
- **Оформление готовых слайдов-образцов шаблона не переносится:** панели, плашки, иконки, стиль диаграмм с образцов. Строки таблицы растягиваются на всё отведённое место, у списков остаётся много свободного места.
- **Ложные предупреждения проверки текста:** латинские названия моделей она принимает за фразу на другом языке, к слайду-плану пишет, что текст не подтверждает заголовок.
- **Шаблон — `.pptx`**, с мастером и хотя бы одним макетом.

## Структура репозитория

```text
src/dpd/              код: разбор шаблона, генерация, вёрстка, аудит, экспорт, рендер
ui/app.py             страница сервиса (Streamlit)
prompts/              промпты моделей, с версиями — prompts/CHANGELOG.md
configs/              модели и параметры запросов, пороги проверок, профили вариантов
tests/                тесты
scripts/              requirements.txt и проверка провайдера модели
deploy/               сервис на своём сервере: HTTPS, пароль, автозапуск
assets/content-pack/  бриф и материалы первого примера
assets/templates/     два шаблона с открытой лицензией (CC BY 4.0) для тестов, атрибуция — в README их папок
examples/             три примера: входные данные и готовые колоды
```

Корпоративный шаблон в репозиторий не входит — он загружается на странице.
