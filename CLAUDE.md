## Проект

«Цифровой дизайнер презентаций» — сервис, который читает чужой шаблон презентации как набор правил и собирает по нему новые слайды по текстовому брифу. Разработка в рамках хакатона.

ТЗ: `docs/00-input/tz.md`. Устав: `docs/00-charter/project-charter.md`.

Сами слои пусты — реализация начинается с T-05. Каталог `prompts/` содержит 14 файлов, все пустые. Задачи реализации с критериями приёмки — в `docs/08-backlog/tasks.md`.

**Реализация начинается с вертикального среза, а не с парсинга.** Задачи T-05 … T-10: контракты, минимальный парсер, минимальная вёрстка, экспорт в PPTX, рендер. Причина — главный технический риск это нативный экспорт: ТЗ не засчитывает слайд, выгруженный растром, и если собрать редактируемые объекты не удастся, обесценится вся остальная работа.

## Главное ограничение

**Сроки вышли** (решение D7). Цель — промежуточный этап, при равных вариантах выбирается более простой.

Промежуточный этап требует ровно четырёх вещей: открытый git-репозиторий, end-to-end прогон на неизвестном шаблоне, девять презентаций (3 шаблона × 3 варианта на одном контенте), видео до 7 минут. Питч, тег версии и воспроизводимый сетап конфиг-файлом относятся к финальной сдаче и с плана сняты.

Исключены из объёма: генерация изображений (задача со звёздочкой, только для топ-10) и фаза 8 — документы алгоритмов в `docs/05-algorithms/` не пишутся.

## Что упрощать нельзя

Семь пунктов, упрощение которых обнуляет результат независимо от сроков:

1. Экспорт PPTX нативными объектами — растровый слайд по ТЗ не засчитывается.
2. Девять презентаций.
3. End-to-end прогон на шаблоне, которого не было в датасете.
4. Аудит внутри пайплайна, с детерминированными и контекстуальными проверками.
5. Три визуально различимых варианта вёрстки.
6. Промпты и конфиги скиллов вне кода, в `prompts/`, с версиями.
7. Экспорт в три формата: `.pptx`, `.html`, `.pdf`.

## Установленные факты о шаблонах

Получены инструментальным разбором, не предположениями. Полностью — в `docs/01-research/template-analysis.md` (11 выводов). Без них легко наделать ошибок:

- **Тема файла врёт.** Во всех четырёх проверенных шаблонах `theme1.xml` расходится с фактическим оформлением: объявляет Arial, используется Play; в одном шаблоне тема содержит дефолтную палитру Office вместо брендовой. Дизайн-токены извлекаются частотным анализом фактической разметки, тема — лишь один из сигналов.
- **Слот не равен плейсхолдеру.** В двух шаблонах из трёх у большинства макетов есть только плейсхолдер заголовка, контент размечен обычными фигурами. Распознавание слотов из фигур — основной режим, не фолбэк.
- **Холсты различаются** (9144000 против 12192000 EMU при одном 16:9). Координаты в схеме шаблона — нормализованные доли, пересчёт в EMU только при экспорте.
- **Наследование свойств — норма.** До 59% текстовых прогонов не несут явного кегля и шрифта. Парсер обязан разрешать цепочку прогон → абзац → макет → мастер → тема. Именно на этом падает presenton.
- **Имена макетов ненадёжны** — в одном шаблоне 11 из 15 называются «Титульный слайд». Тип макета выводится из геометрии слотов.
- **Диаграмм в шаблонах нет ни одной** (138 слайдов-примеров, 0 диаграмм, 0 SmartArt, 4 таблицы). Оформление визуализаций синтезируется из токенов, копировать не из чего.
- **Контраст статически невычислим** в 62% макетов VK Tech: фоном служит изображение. Проверка 4.5:1 — гибридная.

## Окружение

Развёрнуто и проверено измерениями 2026-09-29.

| Что | Где |
|---|---|
| Виртуальное окружение | `D:\venvs\dpd` — Python 3.12.10, 54 пакета плюс сам проект |
| LibreOffice 26.8.0.3 | `D:\LibreOffice\program\soffice.com` |
| Результаты прогонов | `DPD_OUTPUT_DIR`, по умолчанию на диске D |

На диске C свободно менее 4 ГБ, поэтому всё тяжёлое размещается на D. Сам проект остаётся на C: перенос разорвал бы привязку сессий.

**Проект ставится в окружение как пакет:** `pip install -e .`. Пакет живёт в `src/`, и без установки `import dpd` не работает, а тесты падают с `ModuleNotFoundError` — выглядит это как сломанный код, хотя сломан сетап.

**Над проектом работают два человека.** Пути к диску D — с машины владельца, а не требование: код их не знает, всё внешнее задаётся переменными окружения. Замеры производительности сняты на одной машине; какая из двух эталонная для бюджета — открытый вопрос T11, схема ветвления — T12.

**Путь рендера:** LibreOffice конвертирует `.pptx` в PDF, `pymupdf` рендерит страницы в PNG (`pdftoppm` в системе нет). Измерено: конвертация колоды из 29 слайдов — 28 секунд, рендер страницы — 0,11 с. Узкое место — конвертация, и она плохо параллелится: один процесс на колоду.

**Блокер T10:** доступа к API-провайдеру нет, локальный инференс невозможен (AMD Radeon, 15,4 ГБ ОЗУ). Заблокированы генерация и контекстуальный аудит. Не заблокированы парсинг, вёрстка, экспорт и проверки класса `file` — три четверти набора аудита.

## Ключевой архитектурный принцип

LLM отвечает за **смысл**: структуру повествования, тексты, выбор типа визуализации. Детерминированный движок отвечает за **форму**: координаты, цвета, шрифты, соответствие правилам шаблона. Граница проходит по контракту `PresentationStructure`, в котором нет ни одной координаты и ни одного цвета.

Из этого следует воспроизводимость, а на ней держится детерминированный аудит. Соблазн «спросить модель, куда поставить блок» ломает и то, и другое.
